# 03. API: контракт, добавление эндпоинта, генерация

---

## Два контура, и это не деталь

| Контур | Ключ | Кто | Что может |
|---|---|---|---|
| публичный | `pk_…` в вёрстке | аноним, виджет на чужом сайте | каталог, цена, создание заказа, действия по токену |
| серверный | `sk_…`, только сервер | тенант, интеграции | всё остальное |
| сессионный | cookie | сотрудник | админка и стойка по правам |

⚠️ **Публичный API — канал дистрибуции продукта.** Виджет встраивается в чужие сайты, и
после этого контракт изменить нельзя: обновлять свои страницы заказчики не будут. Поэтому
версия в пути (`/v1/…`), внутри версии можно добавлять поля и нельзя убирать.

⚠️ **Токен — не идентификатор.** `/orders/:token` и `/orders/:id` это **разные виды
доступа**: по токену действует неаутентифицированный клиент, по `id` — сотрудник с
проверенным правом. Токен в маршруте персонала означал бы доступ к заказу по знанию
ссылки.

## Добавление нового эндпоинта

Шесть шагов, все обязательные.

```ts
// 1. modules/<модуль>/transport/<имя>.ts — схема на границе
const Body = v.object({ … })                    // valibot, не типы роута

// 2. маршрут
route.post('/v1/admin/things', async (req, reply) => {
  const input = parse(Body, req.body)           // 3. валидация
  const ctx   = await contextOf(req, 'things.manage')   // 4. кто и можно ли
  const result = await createThing(input, ctx, deps)    // 5. service
  return result                                  // 6. форма ответа явная
})
```

⚠️ **Схема valibot не опциональна.** Фреймворк проверяет типы *ответов*, но не тел
запросов — «типизированный fetch» не контракт. Непроверенные данные, дошедшие до домена, —
именно тот баг, ради которого правило существует.

⚠️ **Нормализация — в схеме, один раз.** Телефон канонизируется там же, где валидируется.
`+7 999…` и `8999…` — один человек; ненормализованные они лягут двумя клиентами, потому что
уникальный индекс их не свяжет. Последствия не косметические: лимит активных броней
обходится сменой формата, стойка не находит заказ по телефону, выгрузка по 152-ФЗ отдаёт
часть данных субъекта. Нормализация в схеме означает, что новый эндпоинт **не сможет
забыть** — схема единственный вход.

⚠️ **Никогда не отдавать строки БД как есть.** Ответ собирается явно: иначе внутренние
колонки уезжают клиенту, а переименование колонки ломает фронт.

⚠️ **Право и тариф — две разные проверки.** «Этому сотруднику можно?» и «этот прокат
оплатил?» — разные границы. Проверять по отдельности в каждом обработчике значит однажды
забыть вторую и раздать платную функцию бесплатно. Сначала право, потом тариф: сотруднику
без прав незачем знать тариф проката.

## Генерация API: что генерировать, а что нет

Вопрос был задан прямо, и измерение ответило не так, как ожидалось.

```
эндпоинтов                           80
медиана строк кода                   44
эндпоинтов ≤20 строк (CRUD-подобных) 13
крупнейший (public/orders.post.ts)  341
```

⚠️ **Маршруты генерировать нечего.** Типичный эндпоинт — не «отдай строку по id», а
сценарий: проверить право, проверить тариф, посчитать цену, проверить наличие, создать
заказ, записать согласия, положить уведомление в очередь. Генератор такого не порождает, а
13 тривиальных случаев не окупают генератор.

**Что генерировать стоит** — из схем, которые уже написаны:

1. **OpenAPI** — публичный API нужен внешним разработчикам; документация, написанная
   отдельно от кода, расходится с ним за месяц;
2. **типы ответов для фронта** — сейчас типизировано 22 вызова из 117;
3. **клиент API** — тонкая обёртка, чтобы путь и тип ответа шли из одного источника.

**Параметры в URL** (`/:id`) даёт роутер любого фреймворка — это не генерация, а
маршрутизация. Нужна конвенция, а не механизм.

## Формат ошибок

Один конверт на весь API: HTTP-код плюс машиночитаемый `code`.

```json
{ "error": { "code": "ITEM_JUST_TAKEN", "message": "Эту позицию только что забрали",
             "details": { "alternatives": ["…"] } } }
```

`message` для человека, `code` для кода — виджет реагирует на код, тексты ещё и
переводятся.

⚠️ **Нарушения инвариантов БД — это бизнес-ответы, а не 500.** `23P01` (exclusion) —
«позицию только что забрали», и это **самая частая ошибка в воронке бронирования**: она
обязана приходить с альтернативами, иначе клиент уходит.

⚠️ **Обратная сторона, уже сработавшая:** отображение кодов БД в тексты слишком грубое.
`23514` (CHECK) переводится как «не хватает свободных единиц» — и когда CHECK сработал на
*прайсе*, прокат увидел сообщение про склад на экране про деньги. Если новый CHECK может
сработать вне воронки бронирования, ловить его на месте вызова до общего отображения.

## Версионирование и совместимость

- версия в пути `/v1/…`; заголовок сложнее и ничего не даёт;
- внутри версии: добавлять поля можно, убирать и менять смысл — нет;
- ⚠️ **виджет обязан присылать свою версию** (`X-Widget-Version`), сервер знает минимально
  поддерживаемую и может попросить обновиться. **Не реализовано** (TODO 17.32), и сделать
  это нужно **до** первого чужого сайта: задним числом механизм не добавить, старые
  виджеты будут ломаться молча.

## Списки: пагинация и фильтры

Один стиль на весь API:

- **курсорная пагинация** (`?cursor=…&limit=…`), не `offset`: заказы добавляются
  постоянно, и offset даёт дубли и пропуски;
- фильтры — плоские query-параметры;
- сортировка `?sort=-created_at`.

Здесь и нужна динамическая сборка SQL — не ради сокращения кода, а потому что **условия
неизвестны на этапе написания**:

```ts
const w = new WhereBuilder()
w.add('o.tenant_id = $', ctx.tenantId)          // всегда
w.addIf(f.status,   'o.status = $')
w.addIf(f.branchId, 'o.branch_pickup_id = $')
w.addIf(f.cursor,   '(o.created_at, o.id) < ($, $)')
```

⚠️ **Только плейсхолдеры, никакой конкатенации значений** — иначе это SQL-инъекция,
написанная своими руками.

⚠️ **Имена колонок сортировки — через белый список**, а не из строки запроса.
`?sort=` от пользователя не должен попадать в SQL ни при каких условиях.

## Ограничение частоты запросов

⚠️ **Не реализовано** (TODO 17.28). Единственное, что работает, — счётчик неудачных
попыток входа в таблице (10 за 15 минут); он про подбор пароля, а не про нагрузку.

Нужно по ключу и по IP, со смыслом двойным: и от злоупотребления, и от **парсинга каталога
конкурентами**.

⚠️ При нескольких репликах приложения счётчик обязан быть **общим**, а не в памяти
процесса: иначе лимит умножается на число реплик. Это первое, ради чего действительно
понадобится Redis.
