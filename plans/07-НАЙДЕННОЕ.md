# 07. Найденное при проектировании

Дефекты и долги, обнаруженные при разборе кода под эти планы. Ни один не исправлен —
исправление требует отдельной работы с проверкой.

⚠️ Все воспроизведены на живом стенде или доказаны запросом к схеме. Это не подозрения.

## 1. ⚠️ Новый вариант с поштучным учётом не продаётся никогда

**Серьёзность: высокая.** Товар заведён, количество проставлено, а купить его нельзя, и
система об этом молчит.

### Что происходит

`pool_day` — счётчик ёмкости по дням для категорий с учётом `count`. Строки в него
пишет **только демонстрационный сидер**:

```
INSERT INTO pool_day … FROM generate_series(current_date, current_date + 120, '1 day')
   ← единственное место во всём коде: server/domain/admin/demo.ts
```

В рабочем потоке строки не создаются нигде. А `adjustQuantity` — то, что вызывает админка
при «привезли ещё два борда» — делает:

```sql
UPDATE pool_day SET capacity = GREATEST(0, capacity + $3)
 WHERE tenant_id = $1 AND variant_id = $2 AND day >= current_date
```

Строк нет → обновляется ноль строк → **молча**.

### Воспроизведено

```
создан вариант: 07439e15-…    (категория tracking='count', не из демо)
UPDATE 0                      ← ровно то, что делает adjustQuantity при +5
строк pool_day после +5: 0
```

Наличие считается по `pool_day` → ёмкость 0 → вариант не показывается свободным никогда.
Ни ошибки, ни предупреждения: админка отвечает успехом, в `movement` приход записан,
остаток по движениям верный. Расходится только витрина.

### Почему не заметили

Все существующие варианты пришли из демо-сидера, который заполняет `pool_day` для всех
подряд. Дефект проявится у **первого реального проката**, который заведёт позицию сам.

### Как чинить

Создавать строки при первом обращении, а не ожидать их наличия:

```sql
INSERT INTO pool_day (tenant_id, variant_id, day, qty_booked, capacity)
SELECT $1, $2, d::date, 0, $3 FROM generate_series(current_date, current_date + horizon, '1 day') d
ON CONFLICT (variant_id, day) DO UPDATE SET capacity = pool_day.capacity + excluded.capacity
```

⚠️ Горизонт брать из `limits.maxAdvanceDays` тенанта, а не константой 120 из сидера. И
воркеру нужен тик, продлевающий горизонт вперёд, иначе через `maxAdvanceDays` дней
ситуация повторится.

⚠️ Заодно: сидер заполняет `pool_day` и для `labeled`-вариантов (1194 строки на демо),
которым он не нужен вовсе — ёмкость там считается по единицам. Мусор, который вводит в
заблуждение при отладке.

## 2. ⚠️ Идемпотентность создания заказа не переживёт вторую реплику

**Серьёзность: средняя сейчас, высокая при репликах.**

Проверка-затем-действие без уникального индекса:

```sql
SELECT … WHERE price_breakdown->>'idemKey' = $2    -- прочитали, не нашли
INSERT INTO rental_order …                          -- вставили
```

`pg_indexes` по `rental_order` уникального индекса на ключ идемпотентности **не содержит**
(проверено). Два одновременных запроса с одним `Idempotency-Key` создадут две брони —
ровно тот сценарий, ради которого идемпотентность вводилась.

**Чинить инвариантом в БД** (железное правило 2): колонка `idempotency_key`, частичный
уникальный индекс, `INSERT … ON CONFLICT DO NOTHING RETURNING`.

⚠️ Попутно ключ уедет из `price_breakdown->>'idemKey'`. Снимок цены — доказательство в
споре о деньгах, технический ключ внутри него не к месту.

## 3. Клиент, оставивший только телефон, не получает ничего

**Серьёзность: высокая. Уже заведён как TODO 19.33**, повторяю для полноты.

Почта в форме необязательна, мессенджер на момент заказа не связан (связывание идёт по
ссылке *из* уведомления), SMS в MVP нет. `pickChannel` возвращает `null`, задача умирает в
`outbox`, ссылка на подтверждение не приходит, бронь снимается по таймауту — и об этом
клиент тоже не узнаёт.

На демо-данных: **24 клиента из 32 без единого канала**, 17 заказов в `awaiting_confirm`,
4 уже `expired`.

Решать продуктово; предпочтительный вариант — показывать ссылку прямо на экране после
оформления.

## 4. `orders/expire.ts` не готов ко второму воркеру

**Серьёзность: низкая сейчас, блокирующая при росте. TODO 17.31.**

`outbox` и лист ожидания берут строки через `FOR UPDATE SKIP LOCKED`; `expire.ts` (снятие
броней, просрочка, неподтверждённые) — простым `LIMIT`. Два процесса разберут одни и те же
строки.

Образец в коде уже есть — разошлись именно эти три запроса.

## 5. `X-Widget-Version` не читается

**Серьёзность: средняя, но окно закрывается. TODO 17.32.**

Спека требует, чтобы виджет присылал версию, а сервер умел попросить обновиться. Заголовок
нигде не читается.

⚠️ Нужно **до** первого чужого сайта: заказчики свои страницы не обновляют, и задним
числом механизм не добавить — старые виджеты будут ломаться молча.

---

## 6. Общего ограничения частоты запросов нет

**Серьёзность: средняя. Часть TODO 17.28.**

Работает только счётчик неудачных попыток входа (10 за 15 минут) — он про подбор пароля.
Публичный API ничем не ограничен: ни от злоупотребления, ни от парсинга каталога
конкурентами.

⚠️ При репликах счётчик обязан быть общим, иначе лимит умножается на их число.

## 7. Отображение кодов БД в тексты слишком грубое

**Серьёзность: низкая, но путает.**

`mapDbError` переводит `23514` (любой CHECK) как «На выбранные даты не хватает свободных
единиц». Когда CHECK сработал на **прайсе**, прокат увидел сообщение про склад на экране
про деньги — и это был путь к дефекту замены будущей цены (найден и починен, 19.23).

Если новый CHECK может сработать вне воронки бронирования, ловить его на месте вызова до
общего отображения.

## 8. Линтер красный на унаследованном долге

**Серьёзность: низкая, но `make check` красный.**

7 ошибок `vue/multi-word-component-names` на односложные имена компонентов из коммита
`0ab85ce`. Это фронт, не бэк, но CI падает, а красный CI перестают читать.

Выбор: переименовать (противоречит правилу «имя файла не повторяет директорию» из
`app/CLAUDE.md`) или отключить правило для `app/components/` с объяснением. Второе честнее:
правило придумано против коллизий глобальных компонентов, а автоимпорт здесь выключен.
