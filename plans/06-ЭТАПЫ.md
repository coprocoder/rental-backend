# 06. Этапы: что делать и в каком порядке

Каждый этап заканчивается **зелёной проверкой и работающим приложением**. Ни один не
оставляет систему сломанной — это условие, а не пожелание.

⚠️ Оценки — для одного человека с ИИ-помощником, при том что архитектура уже продумана
(эти документы). Без них было бы вдвое дольше.

---

## Порядок

```
A. Блокирующие дефекты        2 дня   ← ДО всего остального
B. Подготовка в текущем репо  3 дня   ← не трогая Nuxt
C. Переезд                    7 дней  ← BACKEND-EXTRACTION.md
D. Модульная раскладка        4 дня   ← вместе с C, шаг 3
E. Готовность к нагрузке      3 дня   ← когда появятся тенанты
```

⚠️ **A идёт первым и не обсуждается.** Два дефекта из `07-НАЙДЕННОЕ.md` блокируют пилот:
новый вариант не продаётся, клиент без email не получает ссылку. Оба невидимы — система
отвечает успехом. Переезжать с ними значит переносить неработающий продукт.

---

## A. Блокирующие дефекты (2 дня)

| Что | Проверка завершённости |
|---|---|
| `pool_day` создаётся при заведении варианта и продлевается воркером | завести `count`-вариант вне демо, выставить количество, увидеть его свободным на витрине |
| клиент без email получает ссылку (решение из 19.33) | оформить заказ только с телефоном, получить подтверждение |
| сидер не пишет `pool_day` для `labeled` | `SELECT count(*)` по `labeled` = 0 |

⚠️ Оба дефекта — про расхождение «система сказала ок» и «на самом деле нет». Проверять
**сквозным сценарием**, а не unit-тестом: unit прошёл бы и на сломанном коде.

## B. Подготовка, не трогая Nuxt (3 дня)

Всё это полезно само по себе, даже если переезд отложится.

| # | Работа | Проверка |
|---|---|---|
| B1 | уникальный индекс идемпотентности + `ON CONFLICT` | тест: два параллельных запроса с одним ключом → один заказ |
| B2 | `expire.ts` на `FOR UPDATE SKIP LOCKED` | тест: два воркера не берут одну строку |
| B3 | свернуть ~80 дублирующихся запросов в общие функции gateway | `npm run arch` зелёный, число SQL-литералов упало |
| B4 | `WhereBuilder` для фильтров списков | тесты на списки заказов и инвентаря |
| B5 | составные индексы `(tenant_id, …)` | `EXPLAIN` на 100 сгенерированных тенантах без seq scan |

⚠️ B5 требует генератора данных, которого нет. Это отдельная маленькая работа, и она
окупается: без неё все разговоры про производительность — угадывание на двух тенантах.

## C. Переезд (7 дней)

Детали в `../rental/docs/BACKEND-EXTRACTION.md`. Здесь только привязка.

| Шаг | Что | Проверка |
|---|---|---|
| C0 | эталон ответов всех GET + сценарии мутаций | файлы с эталоном лежат в репо |
| C1 | монорепо, `shared` → пакет | `make check` зелёный |
| C2 | **слой usecase**: логика из обработчиков в чистые функции | эталон совпадает; появились тесты usecase без HTTP |
| C3 | второе приложение на Fastify рядом | эталон совпадает против нового порта |
| C4 | переключение фронта одной переменной | приложение работает через новый бэк |
| C5 | удаление `server/` из Nuxt | `make check` зелёный |

⚠️ **C2 — самый большой шаг**, единственный трогающий 80 файлов. Делать эндпоинт за
эндпоинтом, сверяя с эталоном. Именно он делает остальные механическими.

⚠️ **C4 принесёт две вещи, которых не было в одном процессе:** CORS и cookie сессии между
origin. Плюс SSR начнёт ходить в API по сети — появятся таймауты там, где их не было.

## D. Модульная раскладка (4 дня, вместе с C3)

| # | Работа | Проверка |
|---|---|---|
| D1 | девять модулей, вертикальные срезы | каталоги на месте, приложение работает |
| D2 | фасады `*.public.ts` | ни один модуль не импортирует чужие внутренности |
| D3 | правила в `dependency-cruiser` | нарушение границы роняет сборку |
| D4 | тест владения таблицами | запись в чужую таблицу — красный тест |
| D5 | `kernel`: Ctx, ошибки, часы, outbox | домен не импортирует I/O напрямую |

⚠️ **Делать на шаге C3, не раньше.** Пока код в Nuxt, его расположение задаёт file-based
routing — перекладывать дважды значит удвоить работу и риск.

### Семь правил, которые остаются в CI навсегда

```
transport-is-top           никто не импортирует transport
usecase-no-http            usecase не знает Request/Response
domain-no-io               domain не импортирует gateway, integrations, pg
gateway-no-http            gateway не знает про HTTP
module-private-internals   только через *.public.ts
no-module-cycles           цикл между модулями = один модуль в двух каталогах
shared-is-leaf             shared ни от чего не зависит
```

Плюс два теста, которые графом импортов не выразить:

- **дрейф схемы** — `pg_constraint` против ожидаемого списка (уже есть);
- **порядок блокировок** — многодневная бронь из двух модулей одновременно; единственный
  способ поймать нарушение правила 14 до прода.

## E. Готовность к нагрузке (3 дня, когда появятся тенанты)

| # | Работа | Проверка |
|---|---|---|
| E1 | ⚠️ RLS через PgBouncer в transaction pooling | `rls-empty-tenant.test.ts` зелёный через пулер |
| E2 | две реплики за балансировщиком | эталон совпадает, health check выключает упавшую |
| E3 | общий rate limiting | лимит не умножается на число реплик |
| E4 | метрики: время ответа, ожидание блокировок, глубина outbox | графики есть, пороги заданы |
| E5 | секционирование `pool_day` по дате | `DROP` старой секции вместо `DELETE` |

⚠️ **E1 — первый и самый важный.** Это вопрос утечки чужих данных, а не скорости: при
неверном режиме пулинга `SET LOCAL app.tenant_id` теряется, и RLS перестаёт изолировать.
Проверять до нагрузки, а не под ней.

---

## Что НЕ делать ни на одном этапе

⚠️ **Не менять схему БД одновременно с переездом.** Одно изменение за раз — иначе непонятно,
что сломалось. Исключение: B1 и B5 идут *до* переезда и проверяются отдельно.

⚠️ **Не начинать с удаления `server/`.** Пока обе реализации живы, откат стоит одну
переменную окружения.

⚠️ **Не переписывать домен и тесты.** 10 200 строк домена и 322 теста переезжают как есть —
это главная экономия всего плана. Любая работа, которая их трогает, требует отдельного
обоснования.
