# 01. Модули: границы, фасады, владение данными

Главный документ против превращения в легаси. Всё остальное — следствия.

---

## Девять модулей

```
modules/
  booking/        заказ, подтверждение, продление, отмена, лист ожидания,
                  жизненный цикл статусов, нештатные ситуации заказа
  counter/        стойка: выдача, возврат, смена, ревизия
  catalog/        категории, варианты, единицы, движения, списание
  pricing/        прайс, модификаторы, апсейл, лимиты
  availability/   наличие, расписание, блокировки, соседние даты
  fitting/        подбор размеров, DIN
  access/         вход, роли, права, функции тарифа, рубильники
  tenant/         настройки проката, тексты, тема, сотрудники, отчёты
  platform/       регистрация тенантов, ключи API, напоминания
```

Раскладка получена не из головы: я прогнал по ней все 40 существующих доменных модулей.
Восемь областей легли сразу, семь модулей `core/*` **не нашли места** — из них и вырос
`access`, а `outbox` ушёл в `kernel`. Разбор в `../rental/docs/BACKEND-DESIGN.md`.

### Плюс два общих каталога

```
kernel/    Ctx, ошибки, пул и тенантный контекст, журнал, часы, outbox
shared/    типы и чистые функции, общие с фронтом (отдельный пакет)
```

⚠️ **`kernel` — не свалка.** Критерий: туда попадает только то, без чего не работает **ни
один** модуль. Нужно двум модулям из девяти — это не kernel, а модуль, от которого они оба
зависят явно.

## Устройство модуля

Вертикальный срез: внутри модуля свои слои, наружу — один файл.

```
modules/booking/
  http/                маршруты
  service/             сценарии: create-order, confirm-order, extend-order
  domain/              правила, специфичные для брони
  database/            SQL этого модуля
  booking.types.ts     типы модуля: строки БД и доменные формы
  index.ts             ← ЕДИНСТВЕННОЕ, что видят другие модули
```

### Что кладут в фасад

```ts
// modules/booking/index.ts
export type { OrderSummary, OrderStatus }        // типы, а не строки таблиц
export { orderById, ordersOfCustomer }           // чтение — только нужное соседям
export { transitionStatus }                      // единственная точка смены статуса
// НЕ экспортируется: database, SQL, внутренние типы, детали строк БД
```

⚠️ **Фасад отдаёт доменные типы, а не строки таблиц.** Если наружу уезжает
`{ id, tenant_id, branch_pickup_id, … }` как есть — сосед привязался к схеме БД, и
переименование колонки сломает чужой модуль. Это ровно та связность, против которой всё.

## Правило изоляции и как оно проверяется

```js
// .dependency-cruiser.cjs
{
  name: 'module-private-internals',
  severity: 'error',
  comment: 'Модуль виден снаружи только через *.public.ts. Иначе через год всё связано со всем.',
  from: { path: '^modules/([^/]+)/' },
  to:   { path: '^modules/(?!$1/)[^/]+/(?!.*\\.public\\.ts$)' },
},
{
  name: 'no-module-cycles',
  severity: 'error',
  comment: 'Цикл между модулями = один модуль, разложенный по двум каталогам.',
  from: { path: '^modules/' },
  to:   { circular: true },
}
```

⚠️ **Проверка обязательна, договорённости недостаточно.** Сейчас связность уже низкая —
внутри домена всего две межобластные связи (`admin → core, inventory`, `counter → core`).
Это хорошее состояние, и держится оно на вкусе разработчика. Достаточно одного «мне нужно
только одно поле из их таблицы» — и через год вернуться назад будет невозможно.

Отраслевая практика говорит то же: определяющий признак модульного монолита —
**границы, которые нельзя нарушить**, а не папки с красивыми именами.

## Владение данными: где общее правило не работает

Стандартный совет — «каждый модуль владеет своими таблицами, соседи ходят через его API».
Я проверил его на нашей схеме, и в чистом виде он **неприменим**:

| Таблица | Сколько областей обращается |
|---|---|
| `category` | 9 |
| `inventory_variant` | 8 |
| `rental_order` | 7 |
| `order_line` | 7 |
| `branch` | 7 |
| `movement`, `event` | 6 |
| `pool_day`, `customer`, `item` | 5 |

Запретить всем, кроме `catalog`, читать `inventory_variant` — значит превратить каждый
расчёт цены и наличия в цепочку вызовов через фасад, причём **внутри одной транзакции**.
Это не изоляция, а медленный и запутанный способ сделать `JOIN`.

### Правило, которое работает: владение записью, свобода чтения

```
ПИСАТЬ в таблицу может только модуль-владелец.
ЧИТАТЬ может любой модуль — через свой database, обычным JOIN.
```

| Таблица | Владелец (пишет) | Читают |
|---|---|---|
| `rental_order`, `order_line`, `order_token`, `waitlist` | `booking` | counter, pricing, tenant, availability |
| `movement`, `item`, `inventory_variant`, `category` | `catalog` | все |
| `pool_day` | `availability` | booking, counter, tenant |
| `price_rule` | `pricing` | booking, counter |
| `staff`, `staff_session`, `api_key`, `tenant_flag` | `access` | все |
| `branch`, `tenant`, `tenant_text`, `schedule` | `tenant` | все |
| `customer`, `consent`, `agreement` | `booking` | counter, tenant |
| `event`, `audit_log`, `outbox` | `kernel` (через хелперы) | никто напрямую |

⚠️ **Почему запрет именно на запись.** Чтение чужой таблицы даёт устаревшую картину в
худшем случае; запись из двух модулей означает **два места, где живёт правило**, и они
разойдутся. Пример из нашего кода: `capacity` в `pool_day` правили шесть разных мест, и
седьмое стало седьмым шансом забыть — так появилось расхождение, найденное на стенде
(11 вещей физически, 6 в счётчике; витрина не продавала половину парка и не сообщала об
этом).

⚠️ Проверяется тестом, а не глазами: тест читает `INSERT|UPDATE|DELETE` по каталогу
модулей и сверяет с этой таблицей. Новая таблица без владельца — красный тест.

## Как модули общаются

Три способа, в порядке предпочтения.

**1. Прямой вызов фасада — по умолчанию.** Синхронно, в той же транзакции.

```ts
import { priceFor } from '../pricing/pricing.public'
const price = await priceFor(c, { variantId, from, to })
```

**2. Событие — когда вызывающему не нужен результат.** Через `outbox`, который уже
работает: запись в таблицу внутри бизнес-транзакции, разбор воркером.

```ts
await publish(c, 'order.confirmed', { orderId })   // booking не знает, кто подпишется
```

⚠️ **Гарантия «хотя бы один раз»** — подписчики обязаны быть идемпотентны. Одно и то же
событие может прийти дважды.

⚠️ **Не заменять событиями то, что должно быть синхронным.** Цена и наличие обязаны
считаться в той же транзакции, что и создание заказа: асинхронность здесь означает заказ
по цене, которой уже нет.

**3. Общий модуль — когда двум нужна одна логика.** Не копировать и не тянуть друг у
друга, а выделить третий модуль, от которого оба зависят явно.

## Добавление нового модуля

Порядок, который стоит соблюдать буквально:

1. **Назвать вопрос, на который модуль отвечает.** Одним предложением, в терминах
   предметной области. Не получилось — модуль не выделен, а придуман.
2. Создать каталог со срезом `transport/service/domain/database` и файл `index.ts`.
3. Записать владение таблицами в таблицу выше и в тест владения.
4. Зарегистрировать маршруты в списке модулей (единственная правка вне каталога).
5. Прогнать `npm run arch` — новых нарушений быть не должно.

⚠️ **Шаг 1 — главный.** Модуль, названный «utils», «common» или «core», через полгода
содержит половину проекта. Если вопроса нет, это не модуль.

## Правка существующего модуля

- правка **внутри** модуля — ничего не согласовывать, границы держит CI;
- правка **фасада** — это правка контракта: посмотреть, кто импортирует, и поправить
  вместе;
- понадобилось залезть внутрь чужого модуля — **сигнал, что правило живёт не там**. Либо
  расширить чужой фасад, либо перенести правило. Не обходить проверку.

## Объединение общего функционала

Задача упоминает это отдельно, и здесь легко навредить.

**Сначала — правда ли общее.** Два похожих куска могут отвечать на разные вопросы и
меняться по разным причинам. Признак действительно общего: изменение бизнес-правила
обязано поменять оба места **одновременно**, иначе получится ошибка.

**Куда выносить:**

| Что | Куда |
|---|---|
| чистая функция, нужная и фронту | `common/` (пакет) |
| механизм без бизнес-смысла (логи, часы, ошибки) | `kernel/` |
| бизнес-правило, нужное двум модулям | третий модуль, от которого оба зависят явно |
| похожий SQL | ⚠️ чаще всего **никуда** |

⚠️ Про последнее. 353 запроса дают 273 уникальные формы — три четверти SQL существуют в
одном экземпляре, потому что отвечают на разные вопросы. Сворачивать стоит только
измеренные повторы: `INSERT INTO event` (13 раз), `SELECT FROM tenant` (14),
`rental_order JOIN branch` (11) — итого около 80 запросов. Остальное похоже внешне, а не
по смыслу.
