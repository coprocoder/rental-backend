# 00. Цели: что считаем успехом

Документ существует, чтобы через год можно было проверить, получилось ли — и чтобы не
делать работу, которую никто не просил.

---

## Задача

Бэкенд должен **не стать легаси**. Это формулировка заказчика работ, и она не про
производительность: проект разрастётся, его будут дорабатывать месяцами, и главная угроза —
не нагрузка, а момент, когда правка в одном месте начинает ломать другое.

Отсюда два разных вида масштабирования, которые легко перепутать:

| | Что значит | Когда болит | Чем решается |
|---|---|---|---|
| **кода** | добавить модуль, не сломав соседний | с первого месяца доработок | границы модулей, слои, проверки в CI |
| **нагрузки** | выдержать больше тенантов и запросов | когда появятся тенанты | реплики, индексы, секционирование |

⚠️ **Первое важнее и наступает раньше.** Нагрузки пока нет: 2 тенанта, 59 заказов, 14 МБ.
А доработки идут каждый день, и каждая из них — шанс размыть границу.

---

## Критерии успеха

Проверяемые, а не «код должен быть чистым».

### Масштабирование кода

1. **Новый модуль добавляется без правки существующих.** Проверка: добавить модуль,
   `git diff` не трогает чужие каталоги, кроме регистрации в списке маршрутов.
2. **Нарушение границы модуля роняет сборку**, а не проходит ревью. Проверка: временно
   импортировать внутренний файл чужого модуля — `npm run arch` краснеет.
3. **Сценарий тестируется без HTTP.** Проверка: у каждого usecase есть тест, не
   поднимающий сервер.
4. **Правило можно найти за минуту.** Проверка: по слову из бизнес-формулировки
   («продление», «DIN», «неявка») `locate/find.sh` приводит в один модуль.

### Масштабирование нагрузки

5. **Приложение запускается в несколько экземпляров** без расхождения поведения.
   Проверка: два инстанса за балансировщиком, прогон эталона API даёт одинаковые ответы.
6. **Ни один запрос не делает seq scan по таблице тенанта** на объёме 100 тенантов.
   Проверка: `EXPLAIN` на сгенерированных данных.
7. **Изоляция тенантов переживает пулер соединений.** Проверка: тесты RLS через PgBouncer
   в transaction pooling.

## Чего НЕ делаем

Каждый пункт — с причиной, потому что без причины запрет не переживёт первого спора.

⚠️ **Не микросервисы.** Заказ создаётся одной транзакцией БД, в которой участвуют
`pool_day`, `order_line` и `EXCLUDE`-ограничение против двойного бронирования. Разрезав по
сервисам, мы меняем работающие инварианты на сагу с компенсациями — на порядок более
сложную конструкцию ради разделения, которого никто не просил. Инварианты в БД — несущая
конструкция продукта, а не деталь реализации.

⚠️ **Не шардирование сейчас.** Расчёт в `04-ДАННЫЕ.md`: даже 1000 прокатов с пятью
филиалами дают ~900 ГБ за три года, и 850 из них — `pool_day`, который секционируется и
архивируется. Шардирование — последняя ступень лестницы, до неё три более дешёвые.
**Но ключ (`tenant_id`) есть в каждой таблице уже сейчас**, поэтому ступень остаётся
доступной.

⚠️ **Не ORM вместо SQL.** 37% запросов используют `tstzrange`, `&&`, оконные функции,
`FILTER`, CTE, `FOR UPDATE SKIP LOCKED`. Это и есть ядро продукта — подсчёт наличия по
дням и проверка пересечений. В ORM они превращаются в `raw()` с потерей всех преимуществ.

⚠️ **Не абстракция «сменим базу».** Не сменим: на Postgres держатся `EXCLUDE USING GIST`,
`tstzrange`, RLS, частичные индексы. Абстракция ради переносимости, которой не будет,
стоит выразительности, которая нужна каждый день.

⚠️ **Не переписывание с нуля.** Домен (10 200 строк) свободен от веб-фреймворка и
переезжает как есть; 322 серверных теста не импортируют HTTP-слой и переезжают тоже.
Переписывание выбросило бы и то, и другое.

## Принципы, которым следуем при доработках

SOLID и DRY названы в задаче. Ниже — что они означают **в этом проекте**, потому что в
общем виде их можно понимать как угодно.

**Одна ответственность** — у модуля, а не у класса. Модуль отвечает на вопросы одной
области: `pricing` — «сколько стоит», `availability` — «свободно ли». Признак нарушения:
чтобы ответить на вопрос, модуль лезет в чужие таблицы.

**Открыт для расширения** — новый провайдер эквайринга добавляется адаптером, без правки
домена. Это уже правило: `dependency-cruiser` запрещает домену импортировать
`integrations`.

**Подстановка** — все адаптеры одного вида взаимозаменяемы, потому что домен видит наш
тип, а не их DTO. Провайдеров будет несколько, и это не гипотеза.

**Разделение интерфейсов** — модуль отдаёт наружу узкий фасад, а не всё, что умеет.
`booking.public.ts` вместо доступа к его gateway.

**Инверсия зависимостей** — I/O приходит параметром (`deps: { db, clock, notifier }`), а не
импортируется. Часы в зависимостях не педантизм: половина логики зависит от «сейчас»
(снятие броней, дедлайны, сезоны), и без подменяемых часов эти сценарии тестируются только
ожиданием.

**DRY — про знание, а не про текст.** Два одинаковых `SELECT` в разных модулях могут быть
законны: они отвечают на разные вопросы и изменятся по разным причинам. А вот матрица
прав в двух копиях — настоящее нарушение, и оно уже приводило к дефекту (клиентское
«зеркало» разошлось с сервером, опечатка в праве молча прятала пункт меню).

⚠️ **Обратная сторона DRY, про которую забывают:** преждевременное обобщение двух похожих
вещей в одну связывает их навсегда. Если `booking` и `counter` считают что-то похоже — это
повод сравнить, а не немедленно вынести в `kernel`.

## Что уже сделано к моменту написания

Не с нуля: часть подготовки выполнена в основном репозитории.

- домен свободен от H3 — проверяется `dependency-cruiser`;
- слой `gateway` введён, SQL вынесен из трёх обработчиков;
- фронт ходит в API через единственную точку `useApi` — смена адреса бэка это одна
  переменная окружения;
- воркер работает отдельным процессом вне Nitro — доказательство, что вынос возможен;
- 379 тестов зелёные, из них 322 серверных переезжают без правок.
