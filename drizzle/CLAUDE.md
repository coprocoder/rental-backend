# drizzle — schema and migrations

```
0000_complete_unicorn.sql   generated by drizzle-kit from server/db/schema.ts
manual/NNNN_*.sql           hand-written: everything drizzle cannot express
meta/                       drizzle-kit snapshots — machine-generated, do not edit
```

## ⚠️ Never `drizzle-kit push`

It **drops `EXCLUDE` constraints**, and `drizzle-kit check` does not notice — so the schema
silently loses the guarantee against double booking. Denied in `.claude/settings.json`;
that deny is the enforcement, this paragraph is the reason.

Correct flow:

```
npm run db:generate      # drizzle-kit generate → a new SQL file
                         # review the diff: DROP on a constraint is a stop sign
# invariants drizzle cannot express → drizzle/manual/NNNN_name.sql
npm run db:migrate       # generated first, then manual, in filename order
```

`scripts/migrate.ts` records applied manual files in the `_manual_migrations` table and
skips them next run. **Migrations are append-only**: to change an applied one, write the
next number. Editing an applied file is a no-op on any database that already ran it —
that has bitten this project before.

⚠️ A **rename** needs its own guard: adding a column with `IF NOT EXISTS` after the
original was already applied silently does nothing. The fix that worked was an idempotent
`ALTER TABLE … RENAME COLUMN` inside a `DO` block, plus deleting the journal row and
re-running.

⚠️ Write manual SQL **idempotently** (`IF NOT EXISTS`, guarded `DO $$…$$` blocks). Local
databases get reset and re-migrated constantly, and a half-applied file is worse than a
failed one.

## What lives in manual/

Everything that is an invariant rather than a shape (iron rule 2 — *an application-level
check does not close a race*):

- `EXCLUDE USING GIST (… WITH =, period WITH &&)` — no double booking, no overlapping
  price rules. Needs `btree_gist`. Violation raises SQLSTATE `23P01`.
- RLS policies on all 35 tables, plus the `rental_app` role (`NOBYPASSRLS`).
- `CHECK` constraints, partial unique indexes (`23505`), SQL functions such as
  `season_month_active()`.

⚠️ `season_month_active()` is an **SQL twin of `shared/season.ts`**. Change one, change the
other, or the catalog and the availability query disagree about what is in season.

## Verification

`test/invariants.test.ts` reads `pg_constraint` and fails if an `EXCLUDE` constraint went
missing — the drift test that makes rule 11 self-enforcing. Run it after every migration.
