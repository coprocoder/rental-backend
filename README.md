# rental-backend — API проката

Сервис на Node: **Fastify + Postgres**. Здесь схема, миграции, домен и все 78
маршрутов. Фронт — отдельный репозиторий `../rental/` (Vite + Vue).

## Запуск с нуля

Нужны **Docker** (для Postgres) и **Node 20+**.

```bash
npm install
cp .env.example .env     # значения по умолчанию рабочие
make dev                 # Postgres в Docker → миграции → сервис на :3200
make seed                # демо-данные: прокат «demo», инвентарь, заказы
```

Проверить, что поднялось:

```bash
curl localhost:3200/health          # {"status":"ok"}
```

⚠️ `health` отвечает `degraded`, если сервис жив, а база нет — он проверяет
**соединение с БД**, а не отвечает 200 безусловно. Экземпляр, потерявший базу,
обязан выпасть из балансировки.

Фронт поднимается отдельно, во втором терминале: `cd ../rental && npm run dev`.

## Команды

```bash
make check      # то, что гоняет CI: типы, тесты, границы слоёв
make baseline   # сверка ответов с эталоном (нужны оба сервиса)
make psql       # консоль базы
make reset      # снести данные и развернуть заново
```

⚠️ **`make check` не проверяет переезд.** Тесты доказывают, что код делает
задуманное; `make baseline` — что он отвечает **тем же**, чем отвечал Nuxt.

## Главное в одном абзаце

Бэкенд остаётся **одним сервисом** — модульным монолитом, а не микросервисами: заказ
создаётся одной транзакцией, где участвуют счётчик дней, позиции и `EXCLUDE`-ограничение,
и разрезать это по сервисам значит обменять работающие инварианты на распределённые
транзакции. Масштабируется он **репликами приложения за балансировщиком** (состояние в
Postgres, процесс без памяти между запросами) и лестницей на стороне БД: индексы →
секционирование `pool_day` → архив старых сезонов → выделенная БД для крупного заказчика →
шардирование по `tenant_id` как последнее средство. Ключ шардирования уже есть в каждой
таблице, поэтому последний шаг остаётся возможным, но по расчётам не понадобится.

⚠️ Порядок именно такой, и это не наша выдумка — это стандартная последовательность для
мультитенантных SaaS на Postgres. Пропускать ступени дорого: шардирование, введённое
вместо секционирования, добавляет распределённые транзакции туда, где хватало одной.

## Правила этого репозитория

⚠️ **Цифры в планах измерены, а не оценены.** Каждое число получено скриптом по коду или
запросом к БД; где это прогноз — сказано явно. Перед началом работ перепроверить: код
меняется.

⚠️ **План, который нельзя проверить, — не план.** У каждого этапа есть признак
завершённости, который можно предъявить: зелёная проверка, совпавший ответ API, пройденный
тест.

⚠️ **Приватный проект.** Ничего не публиковать, не пушить на корпоративные хостинги.
