# Схема БД и инварианты уровня Postgres

Центральное решение всего проекта: **инварианты живут в базе, а не
в коде**. Проверка в прикладном коде гонку не закрывает — два
обработчика читают «свободно» одновременно и оба записывают.

## Как устроены миграции

Два механизма, и это не дублирование:

| Что | Чем | Зачем |
|---|---|---|
| Таблицы и колонки | Drizzle (`drizzle/*.sql`) | генерируется из `server/db/schema.ts` |
| Инварианты | руками (`drizzle/manual/*.sql`) | `EXCLUDE`, `CHECK`, RLS, функции — Drizzle их не умеет |

Ручные миграции ведут свой журнал `_manual_migrations` и применяются
`scripts/migrate.ts` после Drizzle. Каждая идемпотентна.

:::danger `drizzle-kit push` не использовать
Он сносит `EXCLUDE`-ограничения, а `drizzle-kit check` этого не
замечает. Только `generate` + файл миграции. Есть отдельный тест на
дрейф схемы через `pg_constraint`.
:::

## Двойная бронь — декларативный запрет

Для пер-экземплярных вещей:

```sql
CREATE EXTENSION btree_gist;  -- нужен: смешиваем скаляр (=) и диапазон (&&)

CONSTRAINT order_line_no_double_booking EXCLUDE USING GIST (
  item_id WITH =,
  period  WITH &&
) WHERE (status IN ('reserved','picked_up') AND item_id IS NOT NULL)
```

Детали, которые экономят отладку:

- `tstzrange` полуоткрытый `[начало, конец)`. Возврат в 15:00 и выдача
  в 15:00 **не** конфликтуют. Нужен буфер на подготовку — расширять
  сам диапазон (`end + interval '2 hours'`), а не менять оператор;
- частичный `WHERE` обязателен: отменённые и возвращённые строки
  не должны блокировать перевыдачу;
- нарушение даёт SQLSTATE **`23P01`** — ловим именно его и переводим
  в «эту позицию только что забрали»;
- это **быстрее `SERIALIZABLE`**: SSI берёт predicate lock на весь
  отфильтрованный набор и отваливает транзакции с `40001` даже когда
  интервалы не пересекаются. GIST блокирует только настоящие
  пересечения — нет ретрай-штормов на ложных конфликтах.

## Неоднозначная цена — тот же приём

```sql
EXCLUDE USING GIST (tenant_id WITH =, variant_id WITH =, valid WITH &&)
  WHERE (is_active AND archived_at IS NULL AND rule_kind = 'base')
```

⚠️ `rule_kind = 'base'` в условии обязателен. Первая редакция включала
`rule_kind` в **ключ**, и ограничение запрещало два одновременных
модификатора — а алгоритм разрешения конфликтов требует ровно
обратного. Поймано эталонным тестом движка цен.

## Наличие пула — счётчик по дням

Для взаимозаменяемых вещей exclusion не годится: ограничения попарные,
а нужна **сумма** пересекающихся количеств.

```sql
CREATE TABLE pool_day (
  variant_id uuid, day date,
  qty_booked int, capacity int NOT NULL,
  CHECK (qty_booked <= capacity),
  PRIMARY KEY (variant_id, day)
);
```

`UPDATE ... SET qty_booked = qty_booked + 1` — блокировка строки
сериализует всё бесплатно, инвариант живёт в базе.

:::danger Нельзя считать `SUM(qty) WHERE period && requested`
Это сильно завышает занятость. Брони на 3 и на 10 февраля обе
пересекают запрос «1–15 февраля», но никогда не существуют
одновременно. Нужен счётчик по дням или sweep-line по событиям.
:::

⚠️ Многодневная бронь трогает N строк — **брать их в отсортированном
порядке** `(variant_id, day)`, иначе дедлоки, когда две транзакции
идут по одним дням в разном порядке. Порядок блокировок один на весь
код.

## Изоляция тенантов — RLS, fail closed

RLS включён на **35 таблицах**. Политика:

```sql
USING (tenant_id = current_setting('app.tenant_id', true)::uuid)
WITH CHECK (...)
```

Работа с базой идёт через три функции в `server/utils/db.ts`:

| Функция | Когда |
|---|---|
| `withTenant(tenantId, fn)` | обычная работа: `SET LOCAL app.tenant_id` |
| `withoutTenant(fn)` | поиск по токену, когда тенант ещё неизвестен |
| `getWorkerPool()` | фоновые задачи и записи в обход RLS |

:::danger `app.tenant_id` — только из сессии или ключа
Никогда из тела запроса. Иначе изоляция снимается одним полем в JSON.
:::

## Роли

| Роль | Права |
|---|---|
| `rental` | локальный суперпользователь, `BYPASSRLS` |
| `rental_app` | приложение в проде: `NOLOGIN`, **`NOBYPASSRLS`** |
| `rental_worker` | фоновые задачи, `BYPASSRLS` |

### Найденная дыра: `DEFAULT PRIVILEGES`

⚠️ История, которую стоит помнить. При добавлении таблицы
`tenant_flag` (рубильники, намеренно **без** RLS) был написан
`REVOKE ALL ... FROM PUBLIC`. Тест прав немедленно упал: у `rental_app`
всё равно были `INSERT/UPDATE/DELETE`.

Причина: в схеме объявлены `DEFAULT PRIVILEGES` с грантами на каждую
новую таблицу, а `REVOKE FROM PUBLIC` их не снимает. Прокат мог бы
удалить рубильник, поставленный поддержкой.

Правильно:

```sql
REVOKE ALL ON tenant_flag FROM PUBLIC, rental_app, rental_worker;
GRANT SELECT ON tenant_flag TO rental_app;
GRANT SELECT, INSERT, UPDATE, DELETE ON tenant_flag TO rental_worker;
```

Вывод общий: **проверять права ролей тестом**, а не полагаться на то,
что `REVOKE` сделал ожидаемое.

## Прочие инварианты

| Что | Чем |
|---|---|
| Деньги | `numeric(10,2)`, **никогда** не float |
| Интервалы | `tstzrange`, полуоткрытые |
| Один активный текст на вид | частичный уникальный индекс |
| Один победитель на освобождение | `waitlist_one_winner_uk` |
| Сезон категории | функция `season_month_active()` |
| Диапазон поиска покрывает желаемый | `CHECK (search_period @> period)` |

⚠️ `season_month_active()` — SQL-двойник функции `monthInSeason`
из `shared/season.ts`. Двойник опасен: два места, которые обязаны
совпадать. Поэтому есть тест, сверяющий их на всех 12×12×12 сочетаниях.

## Журнал событий и outbox

Отправка уведомлений **не идёт из транзакции**, меняющей состояние:
упавший SMTP не должен ронять оформление заказа.

```
транзакция: изменить состояние + записать в outbox
   ↓  (отдельно)
воркер: FOR UPDATE SKIP LOCKED → отправить → отметить
```

Повторы с нарастающей паузой, после шести неудач — `dead`.

⚠️ Срабатывания вроде «предложить освободившееся листу ожидания» идут
**через журнал событий**, а не прямым вызовом из обработчика отмены.
Иначе каждый новый способ освободить инвентарь (отмена, досрочный
возврат, снятие по дедлайну) пришлось бы не забыть подключить
отдельно — и однажды забыли бы.

## Токены

В базе лежит **только sha256**. Сам токен существует в ссылке и
не восстанавливается из дампа.

Разные токены на разные действия: `view`, `confirm`, `cancel`, `sign`.
Токен подтверждения **не даёт** права прочитать заказ — это не
перестраховка, а ограничение ущерба при утечке письма.
